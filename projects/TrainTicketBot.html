Проект -

Telegram-бот для отслеживания билетов РЖД

Python python-telegram-bot TG API httpx APScheduler SQLite systemd

В чём заключалась задача?

Разработать Telegram-бота, который автоматически отслеживает появление свободных мест на поезда РЖД по заданным маршрутам и датам, и своевременно уведомляет пользователя. Основные требования:

  • - Поиск станций и поездов через официальный сайт РЖД (pass.rzd.ru) без использования сторонних API или партнёрских сервисов
  • - Интерактивный пошаговый интерфейс в Telegram: выбор станций (из популярного списка или поиском), даты, конкретного поезда, типа вагона (купе/плацкарт/сидячий/люкс) и конкретной полки (верхняя/нижняя)
  • - Возможность подписаться на маршрут, даже если на него ещё не началась продажа билетов — бот автоматически заметит появление билетов
  • - Асинхронная фоновая проверка каждые N минут с уведомлениями трёх типов: «первое обнаружение», «появились новые места» и «билеты всё ещё есть»
  • - Разные режимы уведомлений: «новые места» — со звуком, «билеты ещё есть» — без звука, с возможностью удалять дублирующиеся сообщения и настраивать периодичность
  • - Фильтрация по типу вагона и полке (верхняя/нижняя)
  • - Защита от дубликатов подписок, лимит бесплатных подписок, премиум-доступ через Telegram Stars

Что сделано?

Сердце проекта — взаимодействие с закрытым API сайта pass.rzd.ru. Поскольку официального публичного API у РЖД нет, всю схему работы пришлось восстанавливать экспериментально, анализируя сетевые запросы браузера.

Эндпоинт `pass.rzd.ru/suggester` принимает параметр `stationNamePart` и возвращает JSON со станциями. Первое время запросы возвращали пустой 200 OK — потребовалось добавить заголовки `Origin: https://pass.rzd.ru` и `Referer: https://pass.rzd.ru/`, после чего API начал отдавать данные. Дополнительно реализован кеш популярных станций (17 городов в `config.py`) — при таймауте или ошибке suggester'а бот использует локальный кеш, что делает поиск отзывчивым даже при проблемах с сетью.

Поиск поездов (timetable):
Эндпоинт pass.rzd.ru/timetable/public/ru использует двухфазный протокол на основе RID (Request ID):

  1. Первый запрос с параметрами (code0, code1, dt0, layer_id) возвращает {"result": "RID", "RID": "<uuid>"}
  2. Второй запрос с тем же набором + rid=<uuid> — либо снова RID (нужно повторить), либо {"result": "OK"} с данными
  3. Если за 10 попыток OK не получен — возвращается пустой результат

2. Асинхронная архитектура

Бот полностью асинхронный:

  • httpx.AsyncClient — для HTTP-запросов к РЖД (с таймаутами и поддержкой прокси)
  • python-telegram-bot v20+ — нативная асинхронная обработка команд и callback'ов
  • APScheduler — планировщик фоновых задач (проверка билетов, обслуживание БД)
  • asyncio.wait_for — для ограничения времени выполнения запросов к API (8 секунд на детали вагонов)

Фоновая проверка работает через APScheduler с next_run_time=datetime.now(), чтобы первый запуск происходил сразу после старта, а не после первого интервала.

Сложности

1. Нестабильность API РЖД

API pass.rzd.ru не предназначен для внешнего использования и ведёт себя непредсказуемо:

  • Частые TimedOut и Connection reset by peer — потребовались таймауты (10-15 секунд) и повторные попытки
  • Периодически API возвращает 403 Forbidden для запросов — пришлось настраивать прокси и экспериментировать с заголовками
  • RID-цикл может длиться до 10 итераций; иногда API «залипает», возвращая RID бесконечно — ограничение в 10 попыток с резолвом result != "OK"
  • Разные слои API ведут себя по-разному: layer_id=5827 (поиск поездов) стабилен, layer_id=5764 (детали вагонов) нестабилен и часто падает с таймаутом

2. Обратный инжиниринг API

На начальном этапе пришлось восстанавливать формат запросов вручную:

  • Suggester принимает stationNamePart в верхнем регистре (неочевидное требование)
  • Коды станций — 7-значные числа с лидирующими нулями (например, Москва = "2000000")
  • В ответе timetable поля могут называться по-разному: RID или rid, lst или list
  • Цена может приходить как строка ("—") или число — требуется приведение типов
  • Поле freeSeats может быть числом или строкой — нужна проверка try/except

3. «Слепые зоны» в данных

API не предоставляет прямой информации о доступности билетов «в целом» — приходится агрегировать по вагонам и типам мест. Особенно сложно с фильтрацией по полке (верхняя/нижняя): для этого требуется отдельный запрос к layer_id=5764 на детали каждого вагона, что сильно замедляет проверку.

Ситуация с undef типом сидений (см. выше) была найдена только экспериментально, когда сидячие вагоны стабильно показывали 0 мест при тестировании.
